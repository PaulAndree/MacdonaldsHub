# Proposal

## Why

The approved interface (change 1, `frontend`, design `frontend-design-v1`, contract 0.1.0) runs only on example data. Delivery Hub has no real ingestion, deduplication, confirmation, incident tracking or audit yet, so the administrator cannot use it to claim anything. Change 2 builds the business backend behind the approved contract, and it stops short of sending email: confirming creates incidents and pending outbox records, and change 3 consumes them.

## What Changes

- **Source:** `docs/change_02_backend.md`. Shared context: `docs/project_overview.md` and `docs/architecture.md`.
- **Dependencies:** `platform-base` (archived: containers, Easy Auth identity, allowlist, worker lock, Blob upload mechanism, migrations) and `frontend` (archived, **approved by the administrator on 2026-11-23**: contract `docs/api/openapi.yaml` 0.1.0, tag `frontend-design-v1`). The approval boundary is met, so business logic may be implemented, in the seven ordered phases of the source (section 11). Phase 1 adds no business logic.
- Business schema in PostgreSQL with reversible migrations: batches, staging rows, incidents, outbox, status history, audit, branches and providers. A database constraint guarantees the key provider + order ID, and another guarantees one unconfirmed batch per user.
- XLSX ingestion by the existing single worker: the API grants a create-only upload, the worker verifies the file (SHA-256), reads it, applies the row rules and writes staging. The preview is served from staging. No final incident or outbox row exists before confirmation.
- Exclusive classification of every row (new, duplicate, conflict, error) with reasons and, for conflicts with existing data, both versions; downloadable excluded-rows report.
- Atomic, idempotent confirmation in one PostgreSQL transaction (incidents, outbox, confirmed state, result, audit), safe under concurrency; matches that appear meanwhile are excluded and reported. The confirmed original is copied to the immutable `confirmed` container after the transaction and its integrity verified separately.
- Explicit discard (cancel, and the Cerrar sesión call), no automatic expiry, one unconfirmed batch per user, cleanup coordinated with confirmation in PostgreSQL.
- Incidents: list, detail, export, status history, manual Glovo claim, resolution or rejection with an explicit recovered amount (partial allowed), audited corrections, manual entry with human confirmation.
- Metrics aggregated in PostgreSQL, email and Glovo apart, with the criteria the administrator decided (P-04).
- Audit recording of every operation, append-only. No API or screen to consult it, and none to administer authorizations, roles, branches or providers: the technical team maintains them (RF-18 retired, RF-19 recording only).
- Backend permission enforcement by role for every operation, and a contract test that fails when the OpenAPI generated by FastAPI differs from the approved one (BE-18).
- Integrate the approved frontend with the real API (phase 7), keeping the example build for the `test` demonstration.
- Out of scope: sending email, the email consumer, pause and resume of the queue and its read operation (change 3, `email-sending`; see `design.md`), the real recipients and template text (P-01, P-03), and any administration or audit-consultation screen.

## Capabilities

### New Capabilities
- `audit`: append-only recording of operations, the link between a confirmed batch and its stored original, the minimal audit of a discard, and the absence of any consultation or edit operation.

### Modified Capabilities
- `xlsx-import`: backend reading and validation of the file: structure, row rules, source precision of amounts, dates, Order ID text, fingerprint and identical-file detection, worker processing and recovery after a restart.
- `batch-confirmation`: backend classification and its comparison rules, staging and preview, atomic idempotent confirmation, concurrency, matches found at confirmation, stored original, explicit discard, one unconfirmed batch per user and coordinated cleanup.
- `incidents`: persistence and uniqueness of incidents, state history, queries and export, manual claim, results and corrections, manual entry.
- `metrics`: aggregation from recorded data, channel separation, test and production isolation; the criteria decided in P-04.
- `email-outbox`: creation of the pending outbox records at confirmation with the authorized recipient and template, without sending.
- `identity-access`: backend authorization of every operation by role, allowlist read from the database, and no administration operation.
- `platform`: business schema migrations, initial catalog from configuration, contract test against the approved OpenAPI, integration with real PostgreSQL and Azurite.

## Impact

- **Code:** `src/backend` (domain, services, adapters for PostgreSQL, Blob, XLSX; API routers; worker tasks; migrations; tests), `src/frontend` (real API integration in phase 7), `docs/api/openapi.yaml` only if a change is approved again.
- **Contract:** implements contract 0.1.0 as approved. The three email-queue operations are left to change 3.
- **Dependencies:** an XLSX reading approach that keeps raw numeric text (chosen in `design.md`), a PostgreSQL test harness in CI.
- **Infrastructure:** no new Azure service. The `confirmed` container already exists with version-level immutability, but `platform-base` granted the application identity no write on it, so phase 3 adds the minimal Bicep role needed for the worker to create (never overwrite or delete) blobs there.
- **Pending decisions that gate work:** P-10 (Total relation), P-08 (before real data), P-05, P-01, P-03. None gets a default invented here.
